Study Spot Finder Codebase

What every file does, how a click in the browser turns into a database query and back, and what to watch out for. Written for anyone on the team picking up a part of the code they didn't write.

Describes commit 6f5a442 plus the map work on onemap-implementation
Stack Vue 3 · Vite · Express 5 · Mongoose 9 · MongoDB Atlas

How it fits together

The app is now two programs that talk over HTTP:

  • The client (client/) is a Vue app. It draws every page in the browser and never touches the database. When it needs data it calls a URL starting with /api.
  • The server (everything else) is Express. Its /api routes check who you are, read or write MongoDB through Mongoose, and answer with JSON. They never send HTML.

The old EJS pages are still mounted on the same Express server as a backup. They share the same database and the same login session, so you can use the old and new versions side by side while the team checks the Vue pages.

Vue vs Vite

Vue is the framework the pages are written in and runs in the browser. Vite is a tool on your machine: it serves the Vue files during development, reloads the page when you save, forwards /api calls to Express, and bundles everything for production.

Running it

From the project root:

npm install                  # server packages (root)
npm --prefix client install  # Vue packages
npm run dev                  # starts Express (8000) and Vite (5173) together

Then open http://localhost:5173. Use localhost, not 127.0.0.1; the session cookie is tied to the hostname.

One request, start to finish

Following a login from the click to the screen touches almost every layer, so it's the quickest way to see how the parts connect.

  1. You type your email and password and press Login. The form has @submit.prevent="login", so the browser doesn't reload the page; Vue calls the login() function instead. client/src/views/LoginView.vue
  2. login() calls api('/api/login', { method: 'POST', body: { email, password } }). api() turns the body into JSON and calls fetch with credentials: 'include' so cookies are sent. client/src/api.js
  3. The request goes to localhost:5173/api/login. Vite sees the /api prefix and forwards it, cookies included, to Express on port 8000. client/vite.config.js
  4. Express runs its middleware in order: express.json() parses the body into req.body, then express-session reads the session cookie (none yet) and attaches req.session. server.js
  5. server.use('/api', apiRoutes) hands the request to the API router, which matches POST /login in auth-routes.js and calls userController.apiLogin. routes/api/index.js → routes/api/auth-routes.js
  6. apiLogin lowercases the email, finds the user with User.findOne({ email }), and checks the password with bcrypt.compare. Wrong email or password → 401 { message: 'Invalid email or password' }. controllers/user-controller.js
  7. On success it calls req.session.regenerate() (a fresh session ID, so an old one can't be reused), stores sessionUser(user) in req.session.user, and replies 200 { user }. Express sends a Set-Cookie: connect.sid=… header with the reply.
  8. Back in the browser, api() sees res.ok and returns the parsed JSON. login() sets auth.user = user; because auth is reactive, the NavBar immediately shows your name. client/src/stores/auth.js
  9. router.push(route.query.redirect || '/') moves to the next page. The router guard runs first, calls /api/me, gets your user back (the cookie is sent now), and allows the page. client/src/router.js

Every other feature follows the same path. Only the page, the URL and the controller function change.

Sessions & auth

After login, the browser holds a cookie with a random session ID and nothing else. The user's details live on the server in req.session.user:

req.session.user = {
  id, username, email, school, role, createdAt   // built by sessionUser() in user-controller.js
}                                                // never contains the password hash

Cookies are scoped to a hostname, not a port. That's why logging in on the old localhost:8000/login page also logs you in on the Vue app at localhost:5173.

Why two sets

A redirect is useless to Vue. fetch silently follows it and gets the login page's HTML back instead of JSON, so the page breaks with a confusing error. The api* versions answer with a status code that api.js turns into an error message.

Some checks need the database record, so they live in the controller instead of middleware: author only (edit a review), reporter only (edit a report), and author or admin (delete a review). These compare req.session.user.username with the stored username and return 403 on a mismatch.

Controllers

Each controller file has two halves. The top is the original code that renders EJS. Below the // ---------- JSON API (used by Vue) ---------- line are the new handlers. The new handlers reuse the same model helpers, so both versions read and write identical data.

Every JSON handler follows the same shape:

// METHOD /api/path   (who can call it)
exports.apiDoThing = async (req, res) => {
  // 1. check the input             → 400 { message }
  // 2. check the id is a valid ObjectId (mongoose.isValidObjectId) → 404
  try {
    // 3. load the record              → 404 if null
    // 4. check ownership if needed    → 403
    // 5. do the work, reply           → 200 / 201 / 204
  } catch (error) {
    console.error(error);
    res.status(500).json({ message: 'Error ...' });   // always a JSON answer, never a hung request
  }
};
StatusMeaning in this appExample
200OK, here is the datalist of buildings, updated review
201Creatednew spot, new review, new account
204Done, no bodyany successful delete
400Bad input; the message says what to fixfloor 99 in a 5-floor building, rating 9
401Not logged in, or wrong email/passwordcalling /api/spots logged out
403Logged in but not allowedstudent creating a building, editing someone else's review
404No such record (also used for malformed IDs)/api/spots/abc
409Conflicts with existing dataduplicate postal code or username, approving a request twice
500Something broke on the server; check the terminaldatabase down

Validation lives in small helpers next to the handlers: validateBuilding, validateSpot(body, building) (the floor limit depends on the building), validateReview, and validateReport. Each returns an error message string, or null if the input is fine. Register and edit profile collect several messages and return them as { message, errors: [...] }.

User input is wrapped in String(...) before it goes into a query. That stops someone sending {"email": {"$ne": null}} in JSON to match the first user in the database.

Client (Vue)

Start-up files

index.html is the only HTML page. It loads src/main.js, which does three things:

createApp(App)      // App.vue is the root component
  .use(router)      // turns on URL → page switching
  .mount('#app')    // draws it inside <div id="app"> in index.html

App.vue is the frame: <NavBar /> always on top, then <RouterView />, which shows whichever page matches the URL. Moving between pages swaps only what's inside RouterView. The page never fully reloads, which is why the app feels fast. When you're logged in, App.vue also mounts <MiniMap /> after RouterView, so the map stays loaded while you move between pages.

router.js

A list of { path, component, meta } entries. :name in a path is a parameter: /spots/:id matches /spots/6712f0…, and the page reads it as route.params.id. createWebHistory() gives normal-looking URLs (no #). meta.showMap: true shows the floating minimap on that page; it's set on home and on /building/:name.

Before every page change, router.beforeEach runs:

const user = await auth.fetchMe()                       // GET /api/me
if ((requiresAuth || requiresAdmin) && !user) → /login?redirect=<where you were going>
if (requiresAdmin && !auth.isAdmin)             → /           // home
if (going to /login or /register && user)       → /           // already logged in
The guard is for convenience, not security

Anyone can edit JavaScript in their own browser. The real protection is the apiLoggedIn / apiAdmin middleware on the server. The guard only stops people landing on a page that would fail anyway.

The last route, /:pathMatch(.*)*, catches any unknown URL and redirects to home.

api.js

Every page calls the server through one function:

const spots = await api('/api/spots')                                      // GET
await api('/api/spots', { method: 'POST', body: { name: 'Level 3', ... } }) // body is turned into JSON
  • Always sends the session cookie (credentials: 'include') and the JSON header.
  • Returns the parsed JSON on success. A 204 has no body, so it returns null.
  • On any non-2xx status it throws an Error whose message is the server's message, with .status (the code) and .data (the whole body, e.g. register's errors list).

So every page uses the same pattern:

try {
  spot.value = await api(`/api/spots/${id}`)
} catch (e) {
  error.value = e.message     // e.g. "Study spot not found" — shown in the template
}

Map & directions

This part is on the onemap-implementation branch and isn't merged into configure-vue yet. It uses OneMap, the Singapore Land Authority's free map service, for three things: the map pictures (tiles), turning a postal code into coordinates, and routes.

The browser loads map tiles from OneMap directly, because tiles need no login. Search and routing need a OneMap token, so the browser asks our server, and only the server talks to OneMap.

Building coordinates

To put a building on the map, we need its latitude and longitude. Admins only type a postal code, so the server looks the coordinates up:

  • New buildings: createBuildingJson calls onemap.geocodePostal(postal) and saves lat/lng with the rest of the building. If OneMap fails, the building is still saved, just without coordinates, and the error is logged.
  • Existing buildings: npm run geocode finds every building without coordinates and fills them in, printing ✓ or ✗ for each. A ✗ usually means a wrong postal code. Run it again after fixing; it only retries the ones still missing.

The old EJS add-building page doesn't look up coordinates. Buildings added there need npm run geocode. Postal codes can't be edited, so saved coordinates never go out of date.

services/onemap.js

The only file that talks to OneMap. A services/ file holds code that isn't a route handler or a model, so controllers and scripts can both use it.

FunctionWhat it does
getToken() (private)Logs in with ONEMAP_EMAIL/ONEMAP_PASSWORD and keeps the token in memory until a minute before it expires (tokens last about 3 days), then gets a new one.
search(text)OneMap place search by name, address or postal code. Returns [{ name, address, postal, lat, lng }].
geocodePostal(postal)Returns { lat, lng } for a postal code, or null. Prefers the result whose postal code matches exactly.
routes(from, to)Walking and public transport routes between two "lat,lng" points, and which is faster. Used by GET /api/directions.

Finding the fastest route

  1. Opening a building page loads the building (which now includes lat/lng) and calls mapStore.showBuilding(building). client/src/views/BuildingSpotsView.vue
  2. The store waits until the browser has given your location, then calls GET /api/directions?from=<you>&to=<building>. client/src/stores/map.js
  3. The controller checks that both points really are "lat,lng" numbers (400 otherwise), so nothing else can be slipped into the OneMap URL. controllers/directions-controller.js
  4. The service asks OneMap for a walking route and a public transport route at the same time. Public transport uses the current Singapore date and time and asks for 3 options, keeping the quickest. If one mode fails, the other is still returned; if both fail, the endpoint answers 502. services/onemap.js
  5. Both answers are converted to the same shape. OneMap sends each line as an "encoded polyline" (a compressed string); the server decodes it into a list of points so the browser can draw it straight away.
  6. The store selects the faster route. MiniMap draws it, colouring each part by how you travel, and zooms to fit it. The other route is one tap away. client/src/components/MiniMap.vue
{
  routes: [{
    mode: 'walk' | 'pt',      // pt = public transport
    duration, distance,        // seconds, metres
    legs: [{ mode: 'WALK' | 'BUS' | 'SUBWAY' | 'TRAM' | ...,   // SUBWAY = MRT, TRAM = LRT
             route: '74', from, to, duration, distance,
             points: [[lat, lng], ...] }]
  }],
  fastest: 'pt'
}

The minimap

Drawn with Leaflet (leaflet in client/package.json) on top of OneMap's tiles.

  • Where it lives. App.vue mounts it once, after RouterView, when someone is logged in. It shows itself only on pages with meta.showMap and hides with v-show elsewhere, so the map isn't rebuilt on every page change. Logging out unmounts it, which stops location tracking and clears its state.
  • What's on it. A blue dot for you, purple dots for every building with coordinates (clicking one opens that building's page), a red dot with a label for the building you're heading to, and the route: grey dots for walking, green for bus, red for MRT, teal for LRT. Dark mode switches to OneMap's Night tiles.
  • Buttons. ◎ re-centres on the route, building or you. ⤢ expands the map and lists the steps ("Bus 74 to Blk 306 · 2 min").
Two Leaflet gotchas

Keep the Leaflet map in a plain let, never in ref() or reactive(): Vue's wrapper breaks Leaflet's internals. And Leaflet doesn't notice when its box changes size, so after expanding (and after being hidden) the component calls map.invalidateSize(). Without it, part of the map stays grey.

Legacy EJS app

Nothing from the original app was deleted. The old routers in routes/*.js, the EJS-rendering functions at the top of each controller, and views/*.ejs all still run at localhost:8000. Both versions use the same database and login, so data written in one shows up in the other.

The backup keeps its old bugs

The legacy routes have none of the fixes in the JSON versions. Anyone logged in can edit any review or remove anyone's favourite, /delete has no login check, and unknown emails crash login. Remove the legacy routes before the app goes public.

Adding a feature

The order the existing features were built in. Test the API with curl before writing the page; when something breaks, you'll know which half it's in.

  1. Model. Add or change the schema and helper functions in models/.
  2. Controller. Add handlers below the JSON API line in the matching controller, following the shape in Controllers: validate → load → check ownership → reply with a status code.
  3. Routes. Create routes/api/<feature>-routes.js with apiLoggedIn or apiAdmin on each route. Put fixed paths like /mine before /:id.
  4. Mount. Add router.use('/<feature>', require('./<feature>-routes')) in routes/api/index.js, above the 404 handler. Check the file name matches exactly.
  5. Test the API. curl -c cookies.txt to log in, then curl -b cookies.txt for each endpoint, including the 400 / 403 / 404 cases.
  6. Page. Create client/src/views/<Name>View.vue (PascalCase: AWS runs Linux, which is case-sensitive). Fetch in onMounted with api(), and show loading, error and empty states.
  7. Route. import the page in router.js and add it to routes with the right meta. A missing import gives a blank page.
  8. Link. Add a RouterLink in NavBar.vue or the page that leads to it.
Blank page?

Open the browser console (Cmd+Option+J / Ctrl+Shift+J). The red error names the file and line. The usual causes are a missing import in router.js or a guard that redirects in a loop.

Testing

The conversion was checked with an end-to-end API script (76 checks, all passing). It starts the server against a throwaway database on the same Atlas cluster by setting DB before launch (dotenv doesn't override variables that are already set), runs through every endpoint as three users (student, second student, admin), and drops the database at the end.

It covers the permission rules (student vs. author vs. admin), validation (400s), missing and malformed IDs (404s), duplicates (409s), and the bugs fixed during the conversion. The script isn't in the repo yet. It is a good starting point for the M7 test suite next to the Playwright browser tests.
